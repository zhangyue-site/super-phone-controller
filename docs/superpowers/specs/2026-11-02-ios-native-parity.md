# iOS native parity contract and evidence

## Implemented source

The host `NativeBridge.swift` owns `pcflash/app`, `pcflash/usb`, and `pcflash/screen`. `CaptureContract.swift` stores three bounded JSON records in this project's dedicated shared Keychain access group; no App Group container is required. `BoundedRequest.swift` is the ephemeral, response-bounded, redirect-rejecting HTTP transport. `CapturePipeline.swift` is the shared uploader used by the legacy `SampleHandler.swift` ReplayKit adapter and the iOS 27+ `SCKCaptureSession.swift` ScreenCaptureKit adapter, without writing images or audio to disk. Only video buffers are consumed; microphone UI is hidden.

`pcflash/app`: `appearance` returns `system|light|dark`; `setAppearance({mode})` validates/persists; `info` returns `{versionName,versionCode}`; `openSettings` opens Apple's public app-settings URL; `openDownload` opens the configured HTTPS `DOWNLOAD_URL`, or reports `not_configured`. Diagnostic event payloads are deliberately not persisted; `diagnostics` currently returns an empty JSON array string. This is a documented diagnostics limitation.

`pcflash/screen`:

- `start({ticket,baseUrl})`: validates a 43-character screen-frames ticket and HTTPS endpoint; no user/password/query/fragment URL components. Rejects a USB session. Stores only this short-lived capability plus generation ID, wall-clock and monotonic expiry (270 seconds), and endpoint in the project-specific shared Keychain. On iOS 15–26, the user sees an actual `RPSystemBroadcastPickerView`, must press it and confirm Apple's broadcast prompt. On iOS 27+, `SCContentSharingPicker.shared.present(using: .display)` displays the real system sharing picker; its returned full-display filter creates a `SCStream` with a screen-only output. No subview traversal, synthetic UI events or private API. The Future completes only after the corresponding real stream starts and matching capture state is published. Cancellation and a 60-second timeout revoke the capability and return `cancelled`. Builds made without the ScreenCaptureKit SDK report `capture_sdk_unavailable` on iOS 27+ instead of silently using the removed ReplayKit route.
- `status`: JSON string `{active,capture,task}`. Active requires a valid local capability and extension heartbeat updated within six seconds; merely presenting a picker never reports success.
- `stop`: first removes the local capability, cancels pending consent and requests `/app-screen/stop`. The shared pipeline checks the shared capability before frame work, on responses, and every second even if there are no video callbacks. It cancels work and calls `finishBroadcastWithError` on invalidation. A network request already sent cannot be recalled; server revocation and expiry remain authoritative. No old action is replayed.
- `renewCapture({controlTicket})`: requires the same active broadcast generation. POST `/app-control/screen-renew`, bearer target-owner control ticket, body exactly `{ticket: captureTicket}`; requires response `scope=screen-frames,expiresIn=300` before extending local deadline 270 seconds. The control capability is request-memory-only, never persisted in the Keychain. This is the existing Android/server protocol (see `display_service/app_control.py` and `tests/test_screen_renew.py`), not an invented `/app-screen/renew`. Failed renewal preserves the prior expiry and cannot resurrect a STOP generation.
- USB-specific recovery/window methods return `usb_unsupported`.

`pcflash/usb.snapshot` returns `null`, matching Dart's no-attachment contract; proof/bind/mode operations return an explicit unsupported error. BLE identification remains a separate shared Flutter flow. No USB CDC session or iPhone HID success is inferred from BLE.

## Frame and action barrier protocol

POST `/app-screen/frame`, bearer screen capability, `Content-Type:image/jpeg`, `X-Screen-Sequence`, `X-Screen-Barrier`, `X-Screen-Platform: ios`, and oriented native width/height. The fixed platform header is authorized observation metadata; it grants no additional permission. The full oriented image is scaled within 720×1280 at JPEG quality 0.7, maximum 524288 bytes. Exactly one upload and one newest pending sample are retained. No frame/audio archive or unbounded work queue exists.

The initial barrier is empty. Successful 200/202 responses must carry a 32-character lowercase hexadecimal barrier. After every acknowledged response, the host-clock watermark is advanced and all pending frames are discarded: the next sample must have a later ReplayKit presentation timestamp. This retains the server's action/fresh-frame sequence boundary. Sequence increments serially. Ordinary frames are throttled at 800 ms; a nonzero action barrier temporarily permits 100 ms. Geometry/orientation changes stop capture and require renewed user authorization. `/app-screen/status` is polled every two seconds with at most one in flight; response cap is 16384 bytes. Oversized task presentation is omitted to preserve the shared-state size bound. Frame/control responses cap at 4096 bytes. Redirects are rejected so bearer credentials are never forwarded to redirect destinations.

## Mode-change capture preparation fence

Both capture adapters now consume the existing `/app-relay/usb-window` protocol from the shared pipeline. Every one-second heartbeat starts at most one window request. It POSTs `{operation: "poll"}` with the screen capability. A `prepare` response must have exactly `state,nonce,mode,generation,expiresInMs`: nonce is 32 lowercase hexadecimal characters, mode is `hid` or `normal`, generation is a positive integer newer than all previously accepted generations, and TTL is an integer from 1 through 5000 ms. Booleans, fractional numbers, replayed nonce/generation, malformed fields and already-expired responses are rejected. Nonce history is bounded to 1024 entries per short-lived capture; exhausting it fails closed for further mode changes.

The response lease is conservatively counted from the poll request's start, so network delay cannot extend it. Before acknowledging, the pipeline verifies the same live capability/generation, drops old pending frames and advances its host-clock freshness watermark, then POSTs exactly `{operation:"ready",nonce,mode,generation}` within the remaining lease. Poll and ready requests share one in-flight slot and have at most 1.5-second request timeout. An idle/ready state retains no pending acknowledgement. Any STOP or grant change invalidates callbacks and cancels the window request. Ready is emitted once for a nonce; a lost/uncertain reply is not replayed. The server's existing `Windows.permit` gate remains authoritative.

**This acknowledgement means capture is prepared for the board's intended mode switch. It does not attest to USB CDC presence, USB re-enumeration, or successful iPhone HID input.** The shared pipeline freezes its endpoint at capture start, so a late old-session revocation cannot leak that capability to a newly configured origin.

## iOS 27 ScreenCaptureKit adapter

`Runner/SCKCaptureSession.swift` uses Apple's public `SCContentSharingPickerObserver`, `SCStreamDelegate` and `SCStreamOutput` protocols. It permits full-display filters only, sets native dimensions from `contentRect × pointPixelScale`, attaches only `.screen` output, and disables audio capture. Microphone/camera picker controls are hidden. It does not request camera, microphone or Photos access, create recordings, or buffer video clips.

Each `.complete` video sample is forwarded into the shared bounded uploader. Blank/suspended/stopped samples and system stop/error notifications terminate the session. Idle/nonimage buffers are not reused as fresh post-action frames. `SCStreamFrameInfo.videoOrientation` is applied during JPEG encoding. The sample presentation time is converted from the stream's `synchronizationClock` to the host clock before comparison with action/preparation watermarks; if no clock is available the sample is rejected. Geometry/orientation changes require new consent. System picker errors, denied restrictions, selection cancellation, STOP during start and late start callbacks all have explicit cancellation paths. A stale start callback stops its stream and cannot reactivate an ended generation.

The host Info.plist declares `NSScreenCaptureUsageDescription` and `UIBackgroundModes = ["screen-capture"]` to support an actively consented full-display stream while the app is backgrounded. The ScreenCaptureKit framework is weak-linked in Runner, and all references are iOS-27 availability/SDK guarded. The extension contains neither ScreenCaptureKit nor ONNX linkage; it uses only the shared transport and legacy ReplayKit adapter.

Apple's iOS SDK marks several familiar macOS APIs unavailable on iOS: `queueDepth`, `minimumFrameInterval`, `pixelFormat`, `allowedPickerModes`, `maximumStreamCount`, and content/config update methods. This implementation avoids those APIs; application-owned frame retention is bounded independently of the system stream's internal queue.

## Dedicated shared Keychain storage

The host and extension use the same explicit `CaptureKeychainGroup` Info.plist value and entitlement: `$(AppIdentifierPrefix)$(APP_BUNDLE_ID).capture`. This belongs exclusively to this project's bundle namespace. The previous App Groups entitlement, Info key and unused build variable are removed; there is no filesystem/App Group fallback or reuse of another project's container.

`CaptureContract` preserves `read`, `write`, `clearGrant`, `validGrant` and `base`, and exposes `storageAvailable` for the host's preflight. Only the opaque record names `grant.json`, `status.json` and `endpoint.json` are accepted; those account names no longer identify files. Records use `kSecClassGenericPassword`, service namespace `<resolved-group>.ephemeral-capture.v1`, an explicit `kSecAttrAccessGroup`, and `kSecAttrSynchronizable = false`. Both reads and writes reject JSON above 16384 bytes. Add/update enforces `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`; items do not synchronize across devices and cannot migrate to another device through backup restoration. Keychain reads use a noninteractive authentication context. No screenshots, audio or control-ticket credentials are stored; no keychain values are logged.

A single-record `SecItemUpdate` replaces JSON atomically. A missing record is added; an add race retries update, avoiding a delete/add gap. `clearGrant` removes the capability and potentially sensitive task presentation together; the non-secret endpoint remains as configuration needed for revocation. TTL, monotonic expiry, generation checks, STOP, memory-only frames and user-initiated system consent are unchanged. A previous file-based authorization is not silently migrated or resumed.

`storageAvailable` validates that the group expression resolved to a project-specific identifier and probes only this service/account. It accepts success or an absent record as a read preflight; it is not proof that a signed app may add items, because entitlement rejection can appear as an absent search result. The first actual write must succeed before consent preparation proceeds. Any storage/signing error fails the start; private signing must resolve the App Identifier Prefix in **both** Info.plists as well as the two entitlements, then verify the final signatures' groups agree. This check is separate from successful SDK compilation.

Apple's [shared-Keychain access-group guidance](https://developer.apple.com/documentation/security/sharing-access-to-keychain-items-among-a-collection-of-apps) documents scoped access and entitlement requirements. [Configuring Keychain Sharing](https://developer.apple.com/documentation/xcode/configuring-keychain-sharing) documents the App Identifier Prefix and same-group target configuration. No additional Apple capability or real device access is claimed merely from those references or the profile's wildcard allowance.

This migration was checked only by offline Swift syntax parsing, plist/project validation and source/entitlement contract tests. **No real macOS Keychain read, write, update or delete was executed.** Signed iOS host/extension sharing, lock/unlock, background capture, clean install and STOP still require the appropriate GitHub-built artifact and real-device acceptance.

## Build and signing

The project now contains an embedded `ScreenBroadcast.appex` target, dependency, source membership, sample-buffer extension plist and two matching project-specific `keychain-access-groups` entitlements. Both targets remove the previously required `com.apple.security.application-groups` entitlement. Deployment floor is iOS 15 to match the Flutter/native dependency baseline. Extension version derives from Flutter's Generated.xcconfig; no private provisioning or team identifier is committed.

Private GitHub Actions signing inputs must configure:

- `APP_BUNDLE_ID` (public default `org.example.phonecontroller`);
- `BROADCAST_BUNDLE_ID` (default `$(APP_BUNDLE_ID).ScreenBroadcast`);
- `CaptureKeychainGroup` in both Info.plists and `keychain-access-groups` in both entitlements must resolve to the same `$(AppIdentifierPrefix)$(APP_BUNDLE_ID).capture` string; public source contains build expressions and the example bundle only;
- optional `CONTROLLER_BASE_URL`, `DOWNLOAD_URL` HTTPS URLs; Dart `start.baseUrl` supplies the actual capture endpoint;
- both app identifiers and separate matching host and extension provisioning profiles whose keychain access-group allowance includes this exact project group. This design does not require registering or borrowing an App Group. Do not globally replace `PRODUCT_BUNDLE_IDENTIFIER` for both targets with one identifier.

The new ScreenCaptureKit revision requires a GitHub Actions runner with the iOS 27/Xcode 27 SDK; the first committed ReplayKit candidate remains independently buildable with its original macOS runner. CocoaPods/ONNX runtime resolution and the macOS GitHub Actions build remain the main agent's scope. No iOS app was compiled on the local machine or development server in this task.

## Platform boundary and required acceptance

Apple's current [ScreenCaptureKit overview](https://developer.apple.com/documentation/screencapturekit) documents the iOS 27 replacement of ReplayKit without a broadcast extension, the privacy-purpose string and background-mode configuration. Apple's [iOS capture sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-on-ios) demonstrates the system picker, filter and `.screen` stream-output flow. The [picker reference](https://developer.apple.com/documentation/screencapturekit/sccontentsharingpicker) and [video orientation metadata](https://developer.apple.com/documentation/screencapturekit/scstreamframeinfo/videoorientation) define the public APIs used here. The old [RPBroadcastSampleHandler](https://developer.apple.com/documentation/replaykit/rpbroadcastsamplehandler) route is retained for iOS 15–26 only.

This is source adaptation across both API generations. SDK compilation, codesigning/shared-Keychain entitlement provisioning, system capture availability/consent and physical iPhone behavior are separate acceptance stages. No Apple capability approval or real background/HID success is inferred from API availability. The `persistent-content-capture` entitlement linked in the framework overview is currently documented for macOS VNC, and is not inserted into this iOS app's entitlements as an assumed permission.

Required actual acceptance after signed CI artifact installation: cancel picker, confirm picker, foreground/background host, system Stop Broadcast, lock/unlock, offline upload, TTL expiry, renewal race with STOP, board detach as expressed through Flutter BLE ownership, rotate/restart, same-screen barrier freshness, both board types' real USB HID actions and fresh-frame verification. iPhone HID compatibility is unverified until physically exercised. System UI success, signing success and backend frame receipt must be independently recorded.
